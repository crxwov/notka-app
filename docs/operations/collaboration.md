# Два разработчика: роли, ветки и совместная работа

Нотку разрабатывают **Lexic** и **hackov (Егор, GitHub: [crxwov](https://github.com/crxwov))**.

**Lexic создал первоначальную Нотку**: продукт, дизайн, интерфейс и исходную функциональность. **hackov подключился позже как второй разработчик** и активно помогает с развитием проекта, приложениями, инфраструктурой, интеграциями, исправлениями и проверками. Проект теперь развивается совместно. ИИ-агенты помогают разработчикам; они не являются отдельными владельцами проекта и не заменяют согласование между людьми.

## Ветки и зоны работы

| Ветка | Назначение | Как работать |
|---|---|---|
| `tg-app` | Telegram Mini App, бот, дизайн и связанные изменения backend; основной контекст исходной разработки Lexic | Рабочая ветка агента по правилам репозитория. Проверять, чью задачу сейчас выполняем и нет ли пересечения с другим разработчиком |
| `app-dev` | Клиентские приложения и сопутствующий стек; основное направление участия hackov | Пользовательская рабочая ветка. Агент не переключается на неё для изменений без соответствующего поручения |
| `main` | Общая стабильная версия и источник кода для релиза | Сюда интегрируются согласованные изменения обеих рабочих веток; обновление Git не равно выкладке на сервер |

Это приоритетные направления, а не запрет помогать друг другу. Backend, авторизация, API, хранилища, дизайн-контракты и инфраструктура общие: изменение в одной ветке может повлиять на работу другой. Новые ограничения ответственности или передачи права на ветку не следует придумывать без договорённости разработчиков.

## Перед началом задачи

1. Прочитать `AGENTS.MD`, применимые инструкции и текущий `ROADMAP.md`.
2. Проверить рабочую ветку, `git status`, локальные изменения и актуальные удалённые ветки через `git fetch origin`.
3. Понять, какой разработчик поручил задачу, её область и связи с другой веткой. Не считать проект работой одного человека.
4. Не затрагивать чужие незакоммиченные файлы, не делать reset/force-push и не вливать целую ветку только ради нескольких нужных изменений.
5. Если нужен общий API или формат данных, учесть Telegram и Android одновременно. Проверить реальный код обоих клиентов: их frontend сейчас различается.

Для большой задачи план и результаты сохраняются в Roadmap. Незавершённый чужой Roadmap сохраняется отдельно как paused; полезные общие знания публикуются в `docs/`, а не остаются только в истории чата или на компьютере одного разработчика.

## Интеграция в main

1. Сделать минимальное согласованное изменение в рабочей ветке и проверить его по риску.
2. Просмотреть diff: код, данные и документация другого разработчика не должны случайно попасть в коммит.
3. Перед интеграцией снова получить удалённое состояние и понять состав всех входящих коммитов. Если ветка содержит чужую или не относящуюся к задаче работу, интегрировать только согласованный набор, не весь накопленный diff.
4. Обновить `main` без потери удалённых изменений. Не использовать force-push. При конфликте согласовать поведение общего компонента и сохранить изменения обоих разработчиков.
5. Проверить итоговую версию и push. Убедиться, что удалённый `main` действительно указывает на ожидаемый коммит.
6. Подтянуть опубликованный `main` в рабочую ветку, если это не требует вмешательства в чужую работу. `app-dev` не переписывать автоматически; его разработчик синхронизирует ветку с учётом своей незавершённой разработки.

Обычный merge допустим, когда **весь** набор изменений рабочей ветки согласован. Push в `main` допускается по прямому поручению разработчика; правила не требуют повторно спрашивать подтверждение уже порученного действия.

## Выпуск на сервер

Деплой — отдельное действие владельца/назначенного разработчика релиза. Агент не запускает его в рамках поручения «обновить документацию», «закоммитить» или «запушить в main». На текущем сервере:

```bash
# Перед этим: согласованная и проверенная версия уже в main.
git switch main
git pull --ff-only origin main
bash deploy/push.sh 5.227.61.107
```

Перед выкладкой проверяются `/opt/notka/DEPLOY_INFO`, текущая версия, общий план релиза и незавершённая работа второго разработчика. `NOTKA_FORCE=1` не является обычным способом синхронизации: обход защиты ветки должен быть осознанно согласован.

Скрипт отправляет `git archive HEAD`, а не незакоммиченные файлы, распаковывает код поверх серверного каталога, обновляет зависимости и перезапускает приложение. Успешный `/health` не заменяет проверку музыки и пользовательских сценариев. Детали — [деплой](deployment.md), проверенный срез — [инфраструктура](infrastructure-2026-10-14.md).

## Что агент должен сообщить после задачи

- Что изменено и где находится общий документ/код.
- Что проверено и что осталось неподтверждённым.
- Ветки и коммиты, которые опубликованы.
- Был ли деплой. Не смешивать «в main», «на сервере» и «проверено на устройстве».
- Какие изменения требуют действий или внимания второго разработчика.

Одна тема имеет один основной документ: этот файл — правила сотрудничества; `AGENTS.MD` — обязательные указатели и правила агента; `ROADMAP.md` — состояние текущей задачи; отчёт об инфраструктуре — датированные факты и ограничения проверки. Частную переписку, контакты и секреты в репозиторий не копируем.
