# Совместная работа leksik и crxwov

Нотку разрабатывают **leksik** (автор первоначального продукта, дизайна и функциональности) и **crxwov / hackov / Егор** (подключился позже и активно помогает с приложениями, инфраструктурой и общей разработкой). Агенты помогают своим участникам и учитывают работу обоих.

## Три общих файла состояния

| Файл | Назначение |
|---|---|
| [todo.md](../../todo.md) | Только незавершённые планы, зависимости, решения и критерии приёмки. Проверенный завершённый пункт удаляется; история остаётся в Git |
| [already-work-leksik.md](../../already-work-leksik.md) | Что сейчас делает leksik/его агент, какие области заняты, этапы, результаты, ошибки и следующий шаг |
| [already-work-crxwov.md](../../already-work-crxwov.md) | Такое же подробное состояние crxwov/его агента |

Новые ROADMAP-файлы и отдельные планы чатов не создаются. Подробная текущая работа живёт в своём already-work, общие будущие задачи — в todo. Долговременные технические знания — в существующих docs, продукт и бренд — в PRODUCT.md / DESIGN.md. AGENTS.MD и CLAUDE.md остаются короткими входными инструкциями, чтобы агенты автоматически находили один протокол.

## Обязательная проверка перед работой

1. Сделать git fetch origin и прочитать **свежие версии из origin/main** всех трёх файлов. Например: `git show origin/main:already-work-leksik.md`. Локальная копия в старой рабочей ветке может быть устаревшей.
2. Определить, кто поручил задачу. Имя участника не выводится автоматически из ветки: участник и ветка — разные поля.
3. Сравнить свой scope с чужими файлами, API/форматами данных, серверными действиями и стадиями. Проверить также собственный файл: второй агент того же участника не должен молча перезаписать уже активную задачу.
4. Если есть пересечение с active, сообщить пользователю **кто, над чем и где работает**, и приостановить пересекающиеся правки до согласования. Независимую область можно продолжать.
5. Если запись unknown или устарела, не объявлять другого участника свободным. Сообщить о неопределённости и получить подтверждение для пересекающейся области. Новый прямой запрос пользователя может явно разрешить/разделить scope, но не означает автоматическое стирание чужого состояния.
6. **До существенных правок** опубликовать собственную запись с детальным scope, этапами, критериями и next action. Затем начинать работу.

Эти Markdown-файлы — совместный протокол предупреждения, **не атомарная блокировка**. Два агента могут одновременно прочитать свободное состояние; перед конфликтным действием нужно повторно сверять remote и не полагаться на один старый timestamp.

## Содержимое already-work

В каждом файле обязательны participant, agent, status, updated_at_utc, branch, task/objective, scope (пути + общие контракты/серверные действия), success criteria, стадии/status/dependencies, факты/решения, выполненная проверка, ошибки/неудачные подходы, blockers, next action/resume. Опубликованный timestamp — UTC ISO8601; пользователю время объясняется в его часовом поясе.

Статусы: active, paused, blocked, idle, completed, unknown. Пауза/блокировка не снимает занятость перечисленной области автоматически. При завершении убрать активную reservation, сохранить компактный результат/проверки последней задачи, удалить из todo только подтверждённо выполненный пункт. Не накапливать полный журнал каждой минуты.

После первоначального создания чужого пустого record обновлять можно **только свой** файл. Инициализация leksik сейчас имеет unknown: реальная текущая задача ещё не сообщена. Другой агент не должен подменять её своими предположениями.

## Публикация примерно каждую минуту

- Опубликовать начало задачи до правок.
- Пока агент действительно работает, обновлять remote main примерно каждые 60 секунд, даже если подробная стадия не изменилась; сразу публиковать значимое изменение scope/решения/ошибку и pause/block/completion.
- Запись старше 180 секунд считается **неподтверждённой**, а не свободной. Устаревшее состояние требует выяснения, не автоматического захвата работы.
- Если сеть/доступ/push не работает, сообщить пользователю, сохранить локальное состояние и остановить зависящую от координации пересекающуюся работу. Не говорить «опубликовано» без успешного push.

Git-помощник публикует **один свой already-work файл** поверх свежего remote main с отдельным временным индексом. Рабочая ветка и обычный Git index не используются; незакоммиченный/staged код туда не попадает. Push обычный, без force; при конкурентном изменении main снимок повторно накладывается на свежую базу, до трёх попыток.

Однократная публикация из PowerShell:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File deploy/publish-work-state.ps1 -Participant crxwov
# Для агента leksik: -Participant leksik
```

Heartbeat во время активной работы:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File deploy/publish-work-state.ps1 -Participant crxwov -Watch -LeaseMinutes 5
```

Запускать без видимого отдельного окна. Watch ограничен **пятью минутами по умолчанию**: работающий агент должен его продлевать, если задача продолжается. Это не бессрочный фоновой сервис, который притворяется живым после закрытия чата. При status!=active публикации heartbeat прекращаются. Scope/выводы обновляет сам агент; таймер освежает только timestamp и публикует текущую запись. Это не гарантирует минутный интервал при зависшем Git/сети, и такой сбой надо сообщать.

`-ExecutionPolicy Bypass` относится только к запущенному процессу PowerShell; постоянная системная политика не меняется. Помощник создаёт coordination-коммиты в remote main, поэтому перед интеграцией кодовых изменений нужно снова fetch и согласовать diverged ветки. Не объявлять свежесть локальной main по одному старому HEAD.

## Ветки и интеграция

- tg-app: Telegram Mini App, бот и связанные изменения backend; default рабочая ветка агента.
- app-dev: клиентские приложения и пользовательская работа, главным образом направление crxwov. Не переписывать её автоматически.
- main: общая стабильная версия. Coordination-коммиты разрешены отдельно; runtime-код попадает только в согласованном проверенном составе.

Разработчики помогают друг другу; направления не являются жёстким запретом. API, auth, данные и инфраструктура общие, поэтому нужно учитывать оба клиента. Перед merge/push проверить актуальную remote-историю, diff и чужую незавершённую работу. Нельзя force-push, reset чужих изменений или merge всей ветки только ради нужного файла.

Push в main не означает деплой. Production deploy остаётся отдельным действием владельца/назначенного разработчика релиза; текущая цель — `bash deploy/push.sh 5.227.61.107` из проверенного main. Подробности: [deployment.md](deployment.md), [инфраструктура](infrastructure-2026-10-14.md).

## Чистота репозитория

Не удалять источники, интеграции, полезную документацию, незавершённые требования, личные материалы или секреты под видом уборки. Удалять только установленное лишнее после переноса нужного содержания и проверки ссылок. Удалённые старые task-файлы остаются в Git-истории; пользовательские данные/сборки/локальные кэши не публикуются. Частную переписку не копировать.
