## 1. Модульные тесты сезонных ивентов и Плюса (`tests/events_store_test.py`)

Проверяют бизнес-логику `music_resolver/services/events_store.py` и `music_resolver/services/plus_store.py` в изолированной временной папке.

### Запуск
```bash
python tests/events_store_test.py
```

### Что проверяют 10 тестовых сценариев
1. **Календарь открытия заданий**: в 1-й день ивента (`2026-10-22`) открыто 1 задание, на 5-й день (`2026-10-26`) — 5 заданий, на 10-й (`2026-10-31`) — все 10.
2. **Инкремент и потолок прогресса**: `advance()` корректно увеличивает счётчик задания и ограничивает его значением `target`.
3. **Награда 1-й ступени (`tier_3`)**: при выполнении 3 заданий автоматически разблокируется косметическая тема `atmo_halloween`.
4. **Награда 2-й ступени (`tier_5`)**: при выполнении 5 заданий пользователю начисляются реальные **3 дня Нотка Плюс** в `plus_store`.
5. **Награда 3-й ступени (`tier_10`)**: при закрытии всех 10 заданий суммарно начисляются **13 дней Нотка Плюс** (`3 + 10`), причём повторные вызовы `sync_progress` не начисляют дни повторно.
6. **Честный сброс (`reset_user`)**: сбрасывает прогресс и отзывает только ивентовые дни Плюса, сохраняя дни, полученные по промокодам.
7. **Валидация входных данных**: игнорирует отрицательные `delta` и несуществующие `task_id`.
8. **Монотонность синхронизации**: меньшие значения прогресса с клиента не затирают больший прогресс, уже сохранённый на сервере.
9. **Изоляция пользователей**: прогресс разных `user_id` не пересекается.
10. **Границы дат ивента**: корректный статус до начала (`upcoming`) и после завершения (`ended`).

## 2. Браузерные E2E-тесты по Chrome DevTools Protocol (`tests/e2e.mjs`)

В папке `tests/` реализован беззависимостный E2E-раннер на базе встроенного в Node 22 `WebSocket` (`tests/cdp.mjs`), управляющий headless Chrome / Edge напрямую через **CDP**.

### Как запустить E2E-прогон
1. В первом терминале запустить тестовый сервер на порту `8099`:
   ```bash
   python tests/serve_local.py
   ```
2. Запустить браузер с флагом `--remote-debugging-port=9222` и во втором терминале выполнить:
   ```bash
   node tests/e2e.mjs
   ```

### Что проверяет `tests/e2e.mjs` (38 проверок)
- Загрузку приложения в мобильном разрешении `420x880` и отсутствие ошибок в `console.error` / `pageerror`.
- Прохождение всех 3 шагов онбординга.
- Отрисовку главного экрана, баннера Хэллоуин-ивента и переход в `#screen-event`.
- Интерактивную поимку 5 летучих мышей (`Atmosphere.onCatch("bat")`), автоматическое получение `tier_3` (тема `atmo_halloween`) и `tier_5` (+3 дня Нотка Плюс).
- Сброс прогресса ивента и проверку отзыва дней Плюса.
- Создание плейлиста, добавление треков, редактирование со шредером и генерацию ссылки шеринга (`POST /shared`).
- Работу всех 5 визуальных видов плеера (`cover`, `vinyl`, `cd`, `cassette`, `poster`), вращение пластинки, таймер сна и шторку очереди.
- Работу экранов статистики, настроек звука, выбора атмосферы и экспорта JSON-бэкапа.

## 3. Технические нюансы и известные особенности

### 1. Правило `cache/` в `.gitignore` и модуль `music_resolver/cache/ttl.py`
- В `music_resolver/services/music_service.py` используется импорт `from music_resolver.cache.ttl import TTLCache`.
- В корневом `.gitignore` прописана строка `cache/` (без ведущего слэша), которая в Git игнорирует любую директорию с именем `cache` на любом уровне вложенности — в том числе `music_resolver/cache/`.
- Если при чистом клонировании репозитория папка `music_resolver/cache/ttl.py` отсутствует, убедитесь, что она перенесена или создана, а в `.gitignore` при необходимости используйте `/cache/` (только для корневой папки кэша).

### 2. Куки YouTube на VPS
- На домашнем ПК под Windows скрипт `run_notka.py` автоматически берёт куки из установленного Chrome (`YTDLP_COOKIES_FROM_BROWSER=chrome`).
- На облачных VPS IP-адреса дата-центров часто получают от YouTube ошибку `Sign in to confirm you're not a bot`. Для стабильной работы на сервере экспортируйте `cookies.txt` из браузера (в режиме инкогнито) и укажите путь к нему в `YTDLP_COOKIES_FILE` в `.env`.
