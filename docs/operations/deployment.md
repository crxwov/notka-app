## Текущий сервер

- SSH: `ssh -p 6767 notka` → `egor@5.227.61.107`; внутренний sshd слушает 22.
- Приложение: `https://notka.duckdns.org/app/`.
- Код: `/opt/notka/app`; Python: `/opt/notka/venv`.
- `notka.service` от пользователя `notka`: `run_server.py`, Uvicorn на loopback 8080 и дочерний polling-бот.
- Публичный nginx → локальный Caddy → backend; sing-box/Hysteria обеспечивает часть исходящего доступа.
- Секреты и пользовательские данные существуют отдельно от Git.

Это датированный срез, не гарантия неизменности адресов. Конфигурация внешнего nginx/NAT пока не подтверждена. Старый `94.156.179.229:5463` — прежняя цель, не текущий сервер Нотки.

## Что делает deploy/push.sh

1. Выбирает пользователя/порт: по умолчанию egor/6767; для старого IP — root/5463. Поддерживает NOTKA_SSH_USER/PORT/KEY.
2. Читает DEPLOY_INFO; при несовпадении ветки останавливается, если защита не была явно отключена.
3. Отправляет `git archive HEAD`: только файлы последнего коммита, а не несохранённые изменения или обычные локальные `.env`/data/cache.
4. Распаковывает архив поверх `/opt/notka/app`, меняет владельца, устанавливает зависимости, обновляет yt-dlp/ytmusicapi.
5. Перезапускает приложение, проверяет active и локальный `/health`, записывает ветку/коммит/исполнителя/время в DEPLOY_INFO.

Скрипт не обеспечивает атомарный rollout, удаление исчезнувших файлов или автоматический откат. Если установка зависимостей не подтвердилась, возможна попытка старта с уже установленными пакетами. Health не доказывает воспроизведение.

## Порядок выпуска

Деплой выполняет владелец/назначенный разработчик релиза. Поручение агенту commit/push в main не означает поручение перезапустить сервер.

1. Согласовать набор изменений и влияние на Telegram/Android, API и JSON-хранилища.
2. Проверить рабочую ветку и интегрировать только нужные изменения в актуальный `main`, не теряя удалённые коммиты.
3. Выполнить проверки по риску, опубликовать `main`, проверить commit ID.
4. Проверить текущую запись DEPLOY_INFO и доступность резервной копии.
5. Выполнить с рабочей машины из чистого проверенного `main`:

   ```bash
   bash deploy/push.sh 5.227.61.107
   ```

6. Проверить публичный адрес, поиск, подготовку/Range и изменённые пользовательские сценарии; где требуется, на реальном устройстве.
7. Синхронизировать рабочие ветки с учётом незавершённой работы каждого разработчика.

Не применять `NOTKA_FORCE=1` автоматически. Публикация коммита не обновляет APK; Android assets выпускаются отдельно.

## Команды чтения состояния

```bash
ssh -p 6767 notka "sudo systemctl status notka caddy sing-box --no-pager"
ssh -p 6767 notka "sudo cat /opt/notka/DEPLOY_INFO"
ssh -p 6767 notka "curl -s http://127.0.0.1:8080/health"
```

Журналы: `journalctl -u notka` и `/var/log/caddy/access.log`. Логи могут содержать данные/адреса пользователей или параметры внешних запросов; не публиковать сырой журнал. Не выводить `.env`, cookies, токены и полные proxy-конфиги.

## Новая установка и восстановление

`deploy/setup.sh` — шаблон установки на чистую Ubuntu, принимает домен первым аргументом: `bash setup.sh example.com`. Он создаёт пользователя/venv/systemd/Caddy и базовые правила firewall. Он **не воспроизводит всю текущую топологию** с внешним nginx/NAT, DuckDNS DNS hooks и Hysteria.

После bootstrap отдельно нужны код, приватная `.env`, данные и инфраструктурная конфигурация. Не запускать setup.sh поверх работающего сервера ради обновления документации или обычного релиза.

Копии приложения архивируют `data`, но исключают cookies и не включают `.env`, конфиги служб и `cache/shared`. Наличие читаемого архива не доказывает восстановление всей системы. Полный список подтверждённых фактов, ограничений и следующих проверок — в [отчёте](infrastructure-2026-10-14.md).
